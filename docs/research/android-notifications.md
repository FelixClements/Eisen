# Android Notifications for the Eisen PWA

Research summary: how to deliver notifications to users on Android from the Eisen Svelte PWA, what the platform constraints are, and how they fit Eisen's existing local-first / Cloudflare architecture.

## 1. Two possible notification stacks

Eisen currently ships two Android clients:

1. **Installed PWA** (`clients/pwa-svelte`) built with SvelteKit + Vite PWA. This is the active workstream and the focus of this note.
2. **Native Android app** (`clients/android`) built in Kotlin. Native notifications are also covered briefly for comparison.

For the PWA, Android notifications are delivered through the **Web Push API** and displayed by the **Notifications API** in a service worker.

## 2. Web Push API and the notification path

The W3C Push API lets a web application receive messages pushed from a server, even when the app is not in the foreground or loaded.

> "The Push API enables sending of a push message to a web application via a push service. An application server can send a push message at any time, even when a web application or user agent is inactive. The push service ensures reliable and efficient delivery to the user agent. Push messages are delivered to a Service Worker that runs in the origin of the web application."
> — [W3C Push API, ED](https://w3c.github.io/push-api/)

High-level flow for the PWA:

1. App registers a service worker.
2. Service worker subscribes to `PushManager` with an `applicationServerKey` (VAPID public key).
3. Browser returns a `PushSubscription` containing an `endpoint` and per-subscription encryption keys.
4. App sends the subscription to the Eisen backend.
5. Backend POSTs an encrypted message to the `endpoint`.
6. Browser wakes the service worker and fires a `push` event.
7. Service worker calls `registration.showNotification(...)` to display the notification.

## 3. Service workers are mandatory on mobile

The `Notification()` constructor available on the main thread throws on most mobile browsers. Persistent notifications must be shown from a service worker.

> "They are created by calling `ServiceWorkerRegistration.showNotification()` from inside a service worker and fire `notificationclick` and `notificationclose` events on the `ServiceWorkerGlobalScope`."
> — [MDN: Notifications API](https://developer.mozilla.org/en-US/docs/Web/API/Notifications_API)

In `clients/pwa-svelte` the service worker is generated by `@vite-pwa/sveltekit`. The generated worker will need an `importScripts` or injected `push`/`notificationclick` handler. Alternatively, configure `workbox.navigateFallback` and provide a custom `sw.ts` or `sw.js` registered through `src/app.html`.

## 4. VAPID and application server keys

VAPID (Voluntary Application Server Identification) authenticates the Eisen backend to the browser's push service.

> "The FCM Web interface uses Web credentials called Voluntary Application Server Identification, or VAPID keys, to authorize send requests to supported web push services."
> — [Firebase Cloud Messaging: Web get started](https://firebase.google.com/docs/cloud-messaging/web/get-started)

> "VAPID ... allows the push service to confirm which site is sending messages. ... You no longer need a Firebase project, a `gcm_sender_id`, or an `Authorization` header."
> — [Chrome for Developers: Web Push Interop Wins](https://developer.chrome.com/blog/web-push-interop-wins)

Generate keys with:

```bash
npx web-push generate-vapid-keys
```

The **public key** is served to the client and passed to `pushManager.subscribe({ userVisibleOnly: true, applicationServerKey: <publicKey> })`. The **private key** lives only in the Eisen Worker / backend and signs the JWT for each push request.

## 5. Android permissions for PWA notifications

For **native Android apps**, Android 13 (API 33) introduced the `POST_NOTIFICATIONS` runtime permission:

> "Starting with Android 13, all apps must ask users for permission before sending notification prompts."
> — [Android Open Source Project: Notification permission](https://source.android.com/docs/core/display/notification-perm)

For a **PWA on Android**, the permission request is delegated to the browser:

```js
Notification.requestPermission().then(permission => {
  if (permission === 'granted') {
    // subscribe to PushManager
  }
});
```

Chrome on Android will surface the standard browser permission prompt. If the user denies it, the PWA cannot request it again until the user changes the site permission in Android's Settings > Apps > Chrome > Notifications.

Samsung Internet and other Chromium-based browsers on Android generally follow the same Push API / Notifications API support as Chrome.

## 6. iOS vs Android differences

Eisen also targets iOS. The key differences:

- **Android**: Push works from both browser tabs and installed PWAs.
- **iOS**: As of iOS 16.4+, Web Push requires the PWA to be added to the Home Screen and uses the Apple Push Notification service (APNs) behind the scenes for Safari.

This means a single Web Push subscription model works for both, but the user must be on a supported browser/Safari version and, on iOS, must have installed the PWA.

## 7. Displaying the notification

The service worker receives the push and shows it:

```js
self.addEventListener('push', event => {
  const data = event.data?.json() ?? {};
  event.waitUntil(
    self.registration.showNotification(data.title ?? 'Eisen', {
      body: data.body,
      icon: '/icon-192x192.png',
      badge: '/badge-96x96.png',
      tag: data.tag ?? 'eisen',
      data: { url: data.url ?? '/' }
    })
  );
});

self.addEventListener('notificationclick', event => {
  event.notification.close();
  const url = event.notification.data?.url ?? '/';
  event.waitUntil(
    clients.matchAll({ type: 'window', includeUncontrolled: true })
      .then(windowClients => {
        const client = windowClients.find(c => c.url === url);
        if (client) {
          return client.focus();
        }
        return clients.openWindow(url);
      })
  );
});
```

> "You can handle event actions using `event.action` within a `notificationclick` event handler."
> — [MDN: notificationclick event](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/notificationclick_event)

## 8. Web Push Protocol and payload encryption

The backend must speak the Web Push Protocol (RFC 8292 for VAPID, RFC 8291 for message encryption). The payload is AES-128-GCM encrypted per subscription so that the push service cannot read it.

> "Two RFCs stand between you and that notification: RFC 8292 (VAPID, a signed JWT proving the push came from your server) and RFC 8291 (the payload must be encrypted, per message, for that one subscription)."
> — [DEV Community: Waking a dead service worker with Web Push from a Cloudflare Worker](https://dev.to/mfauveau/waking-a-dead-service-worker-with-web-push-from-a-cloudflare-worker-1jnm)

The `Authorization` header format is important:

> "FCM rejects the VAPID Authorization header. The library emits the older draft-01 form, `Authorization: WebPush `, and FCM (behind Chrome/Android) rejects it with `invalid JWT provided` (403). Rewrite it to the draft-02 form, `vapid t=, k= `, and it returns 201."
> — [DEV Community: Web Push without login on Cloudflare Workers](https://dev.to/aulvem/web-push-without-login-anonymous-device-tokens-on-cloudflare-workers-3g48)

## 9. Backend options for Eisen

Eisen's backend runs on Cloudflare Workers. Options for sending push:

1. **`@mmmike/web-push`** (zero-dependency, Web Crypto, edge-runtimes): https://github.com/MMMikeM/web-push
2. **`web-push`** (Node.js, not directly edge-compatible): https://www.npmjs.com/package/web-push
3. **Hand-rolled Web Crypto** in the Worker using the snippets above.

Cloudflare's own documentation also recommends using the Web Push API from an agent/Worker:

> "By combining the agent's persistent state (for storing push subscriptions), scheduling (for timed delivery), and the Web Push API, you can reach users who are completely offline."
> — [Cloudflare Agents: Push notifications](https://developers.cloudflare.com/agents/guides/push-notifications/)

Store push subscriptions in D1/R2 (or as part of the account/device record) and dispatch from a Worker. The subscription object contains no sensitive plaintext, but it is a routing token. Protect it as account metadata.

## 10. Native Android app alternative

If Eisen ever wants richer notifications in the native Kotlin app (`clients/android`), the path is:

- Declare `<uses-permission android:name="android.permission.POST_NOTIFICATIONS"/>` in `AndroidManifest.xml`.
- Create a `NotificationChannel` before posting on Android 8+.
- Request `POST_NOTIFICATIONS` at runtime on Android 13+.
- Post via `NotificationManagerCompat.notify(...)`.

For server-to-device delivery in the native app, Firebase Cloud Messaging (FCM) is the standard Android push transport. Eisen would need a Firebase project and the FCM SDK in the native app. This is separate from the Web Push VAPID flow used by the PWA.

## 11. Limitations and gotchas

- **Doze / App Standby on Android can delay push** until the next maintenance window. High-priority FCM messages wake the device, but Web Push through FCM does not use the same priority flags unless you use the proprietary FCM API directly (which would require a Firebase project and is not the standard Web Push protocol).
- **Service worker eviction**: Android Chrome may kill a service worker under memory pressure. The Push API is designed to wake it again on the next push.
- **Permission cannot be re-prompted** silently after denial. Design the UI to ask the user to enable it in browser settings.
- **Notification click behavior** is limited in service workers: no `window.open`; use `clients.openWindow`/`clients.focus`.
- **Web Push payload size limit** is roughly 4 KB (4096 bytes). Larger data must be delivered as a sync fetch after the user clicks the notification.

## 12. Recommended next steps for the PWA

1. Generate and store VAPID keys as Wrangler secrets (`VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`).
2. Add a `GET /api/vapid-public-key` Worker endpoint to serve the public key.
3. Add a "Notify me" toggle in `settings/+page.svelte` that:
   - Requests `Notification.requestPermission()`.
   - On grant, subscribes via `registration.pushManager.subscribe(...)`.
   - POSTs the `PushSubscription` to the backend.
4. Extend the generated service worker (or add a custom `sw.ts`) with `push` and `notificationclick` handlers.
5. Add a Worker endpoint or queue consumer to encrypt and POST the Web Push payload.
6. Test on Android Chrome installed PWA and Samsung Internet; keep iOS Home Screen PWA testing in mind.

## 13. Local-only reminders and the end-to-end-encrypted task constraint

### Your understanding is correct: the Worker does not know the plaintext reminder

Eisen stores the encrypted task in `vault_records.encrypted_blob` and the Worker only sees opaque fields:

```sql
CREATE TABLE IF NOT EXISTS vault_records (
  record_id TEXT PRIMARY KEY,
  owner_id TEXT NOT NULL,
  encrypted_blob BLOB NOT NULL,
  modified_at INTEGER NOT NULL,
  ...
);
```

The local Dexie `Task` schema keeps `reminderAt` and `dueDate` in plaintext so the UI can render and sort them, but those fields are **not** in the sync payload the Worker can read. They are inside the AES-256-GCM ciphertext. So the Worker cannot, by itself, decide "this task has a reminder at 14:00, send a push now."

### Is a purely client-side / local-only reminder possible?

Yes and no. The *rendering* of the notification is client-side (in the service worker), but the *trigger* at the right time is the hard part on the web platform today.

| Approach | Can it be local? | Works when PWA is closed? | Exact time? | Notes |
|---|---|---|---|---|
| `setTimeout` / `setInterval` in the page | Yes | No | Yes-ish | Only while the page is open. |
| `setTimeout` inside a service worker with `event.waitUntil` | Yes | Sometimes | Yes-ish | Android Chrome often kills the service worker after ~20 minutes of inactivity. Not reliable for long delays. |
| `Periodic Background Sync` | Yes | Yes | No | Browser decides when to fire. Good for "check once a day", not for a 14:00 reminder. Chrome/Edge only; requires installed PWA; not on iOS. |
| `Notification Triggers API` | Yes | Yes | Yes | Exactly the right API, but Chrome's origin trial ended and the team decided not to ship it. |
| Web Push from Worker | No (network) | Yes | Yes | Standard, reliable, but requires the server to know *when* to push. |
| Native Android `AlarmManager` | Yes | Yes | Yes | Requires the Kotlin native app or a TWA wrapper. |

> "The development of Notification Triggers API, part of Google's capabilities project, is no longer pursued."
> — [Chrome for Developers: Notification Triggers](https://developer.chrome.com/docs/web-platform/notification-triggers)

> "You can achieve similar once-a-day functionality, without any guarantees about when during the day the event will fire, by using the Periodic Background Sync API. If your users needed exact control over when the notification is shown, this wouldn't help."
> — [Stack Overflow: Can a PWA schedule notifications when closed?](https://stackoverflow.com/questions/70611006)

### A local-first hybrid that preserves privacy

Because the Worker cannot see `reminderAt`, a true Web Push flow would require leaking some metadata. A middle ground is to keep the *decision* on the client but use the Worker only as a wake-up alarm:

1. The client scans its local `tasks` table and finds the next upcoming `reminderAt`.
2. It sends the Worker a tiny encrypted/opaque record: `{ deviceId, wakeAt: <unix_ms>, nonce: <random> }`.
3. The Worker stores only that single "next wake" timestamp per device.
4. At `wakeAt`, the Worker sends a generic, empty push to that device.
5. The PWA service worker wakes, reads local `reminderAt` values, and shows the actual reminder.
6. The client then computes the *next* `reminderAt` and reschedules.

This way the Worker never learns *which* task or *what* the reminder is; it only knows there is a wake-up at a given time. It still requires Web Push and an online Worker, but the sensitive data stays on the device.

### Bottom line

- A completely offline PWA alarm without any server is **not reliably possible** on Android today because the platform lacks a shipped local alarm API.
- The Worker's lack of plaintext `reminderAt` is a real constraint and your assumption is correct.
- The simplest practical options are: (a) accept a best-effort in-app reminder that only fires while the PWA is open, or (b) use the Worker as a privacy-preserving wake-up clock via Web Push.
